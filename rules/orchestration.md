# 编排细则

宪法指针文件：派发子代理前必读。来源：cc-base `workflow-orchestration` + opencode-base fan-out 判据 + ccb-base 有界对抗。

## 角色与派发

- 主 Agent = 唯一编排者：需求分析、任务拆分、排序、派发、验收。子代理不再派子代理（扁平，depth=1）。
- 派发用 Agent 工具启动 fresh 实例，传入宪法「派单六字段」完整上下文；回传必须以「回执信封六字段」开头。
- 9 角色契约（职责/非职责/话术）见 `docs/ROLE-CONTRACTS.md`：
  implementer / code-reviewer / tester / deployer / researcher / impact-analyst / feedback-observer / evolution-runner / progress-recorder。
- 派静默子代理/长后台任务前先一句话告知用户（静默运行+预计耗时），别让用户对着无输出干等。
- 工具调用被用户消息中断是机制信号 ≠ 否决方案：有新指示照办、只是提醒就解释并重发、不确定先问。

## fan-out 判据（何时并行）

判据轴 = **「决策要不要自洽」**（不是任务数量）：

- **fan-out 甜区**（只读、可汇总、无需互相一致）：多维代码审查、批量写测、代码库探索/研究、多方案独立调研。
- **默认串行**（需决策一致性）：编码、架构设计、契约变更、发布。
- 并行写需：独立 worktree / 互斥 ownedPaths / integration owner 收口。
- 成本闸门：多子代理并行约 15 倍 token，必须用户显式 opt-in。
- 三铁律：主 Agent 唯一编排者；验收判断权留主 Agent；写测独立于被测作者。

## 模型选择（按复杂度）

| 任务特征 | 选择 |
|---|---|
| 机械实现（1-2 文件 + 完整 spec） | 便宜/快模型 |
| 集成判断（多文件、跨模块） | 标准模型 |
| 架构设计/审查/对抗攻击 | 最强模型 |

## 有界对抗（防检视死循环）

- review → fix 循环封顶 **2 轮**；到顶仍有分歧 → 转 deferred（结构化记录：问题/严重度/为何不修/负责人/轮次封顶），不阻其它线。
- red-blue-review 封顶 2 轮；Red finding 必须附 file:line 或复现路径，否则不立案。
- 失败连击 3 次 = 诊断问题而非重试问题：停下换假设，跑 `risk scan` 看历史。

## 验收纪律

- 验收只认客观证据（宪法纪律 5）；子代理自报 DONE 只是「它跑完了」。
- 编码/修复 → 复核 diff + 编译输出 + 对照 Spec 逐条。
- 测试 → 复核测试运行器真实输出 + exit code（不是一句「测试通过」）。
- 部署 → 独立核验三件套：产物时间戳+镜像 tag / 健康检查端点 / live 冒烟验证新功能（勿看「Up 时长」）。

## 接收审查意见

不表演式认同：禁「你说得对/好建议/这就改」空话——要么复述对方技术要求确认理解，不清楚先问，有技术理由就顶回去；确认无误直接动手。

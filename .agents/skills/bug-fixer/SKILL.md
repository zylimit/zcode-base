# bug-fixer：缺陷修复

## 流程

1. **复现**：先拿到可复现路径（命令/操作步骤/输入数据）。不可复现 → 先向用户要信息，不盲改。
2. **red-locks-the-bug（铁律）**：派 tester（与原作者不同的 fresh 实例）先写**锁定该缺陷的失败测试** → 主 Agent 亲验测试为**红** → 才允许动实现。没红过的测试不算锁定。
3. **定位**：读代码/日志/堆栈；大仓先 `node runtime/zbase.mjs impact --paths <相关文件>` 圈受影响面。禁「看起来像这里」就动手——先有证据（能解释症状链）。
4. **最小修复**：只修根因，不顺手重构、不扩范围；遵循现有模式。
5. **修绿**：失败测试转绿；跑受影响模块的回归（impact 的 fanout 范围）。
6. **落账收口**：`receipt write`（含修复前后证据）→ code-reviewer 复审 → 三文件同步。

## 纪律

- 同一缺陷二次出现 = 系统性问题：升级为主 Agent 讨论防护机制（测试/hook/契约），不是再修一次。
- 修复引入的新行为变化，按 dev-builder 的验证纪律走。
- 回归类缺陷（「上次说改了又出现」）优先检查测试是否真的存在且在跑，而不是重写实现。

## 回执

根因解释 + 红绿测试证据 + 受影响回归结果 + receipt seq。

# product-spec-builder：需求规格

## 目标

把模糊想法变成可验收、可签字的 Product-Spec.md。需求质量是后面所有阶段的天花板——这里含糊，后面全歪。

## 流程

1. **澄清访谈**：用户角色与场景 → 核心问题 → 成功判据。追问到底：不接受「类似 X」「智能一点」「更好的」这类模糊词；每个功能问「没有它会怎样」。
2. **规模定档**：S（单模块）/ M（跨模块）/ L（新子系统）。档位决定后续架构/DFX 是否强制。
3. **写 Spec**（模板参考 `harness/templates/`，落项目根 `Product-Spec.md`）：
   - 用户故事与场景（含反例：不做什么）
   - 功能需求（REQ- 编号，每条可验收）
   - 非功能需求（五性初步档位建议——定档在 DFX 阶段细化）
   - 边界与依赖（明确 Out of Scope）
   - 开放问题清单（不许隐藏未决项）
4. **签字闸**：请用户确认当前这版；内容变更须重新请批（rules/workflow.md 签字闸）。
5. **建 CHANGELOG**：首次创建 `Product-Spec-CHANGELOG.md`；此后需求变更**成对更新** Spec + CHANGELOG（只改一个不算完成）。

## 纪律

- 禁止替用户回答开放问题；列出来让用户拍板。
- 每条 REQ 必须可验证（能写出「跑什么命令/做什么操作算过」）。
- 修订时先读现有 Spec 全文，增量修改，不重写风格。

## 回执

产出文件 + 待签字确认项清单 + 开放问题数。

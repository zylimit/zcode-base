# product-spec-builder：需求规格

## 目标

把模糊想法变成可验收、可签字的 Product-Spec.md。需求质量是后面所有阶段的天花板——这里含糊，后面全歪。本 skill 是全链业务理解的唯一源头：架构需求映射、DEV-PLAN、派单信封 Business 字段全部回指 Spec 的业务上下文章节，这里写空，下游每一跳都在猜。

## 流程

### 0. 触发分流（深度自适应）

- **S 档**（单模块/可逆/需求清晰，如「改按钮文案」「加一个字段」）：不走完整采访。一段三段式复述（我理解：…；我假设：…；请纠偏）→ 用户确认后写精简 Spec——业务上下文 3-5 行，四要素各一句即可。杀鸡不用牛刀。
- **M/L 档**（跨模块/新子系统/不可逆面大）：走完整采访协议（动作 1-7）。
- **用户明确委托判断**（「你决定」）：承担判断，推断全部显式标【推断】，不反复问——用户委托的是判断力，不是把提问权再买一遍。
- 分流拿不准 → 按高一档走：仪式成本是一次对话，理解错误成本是整条链返工。

### 1. 采访协议七动作（M/L）

1. **先观察后提问**（apprentice）：提问前先读现有代码/文档/日志/数据；提问必须引用观察证据（「我看到 X，是否因为 Y」），禁凭空问卷——没观察过的提问是把考古外包给用户。
2. **先查后问**：能自查的歧义（代码里有没有现成实现、文档里有没有写过）自查后报「我查到 X，假设 Y」；只问用户才能裁决的分叉。
3. **问题预算**：每轮 ≤2-3 个、选择题优先（给 2-3 个具体选项）、一次打包、参考锚定（「像 X 还是像 Y」）；用户答「都行」→ 用选项代价逼出偏好，不接受含糊。
4. **带假设直答**：材料够时直接给 best-effort 方案 + 假设清单，不空手等——tie 偏直答，防 over-ask。
5. **五个必问主题**：为什么做（什么事让**现在**要做）/ 谁真正受益（谁的手上变轻松、变多轻松）/ 现实中怎么运转（流程/环境/谁在什么情境用）/ 例外与隐性规则（什么时候不该这样、上次出过什么事）/ 成功判据（三个月后怎么知道做对了）；每个功能追问「没有它会怎样」。
6. **example mapping**：每条 REQ 挂至少一个具体 example（真实输入→预期输出/操作序列）；问不出的 example 进开放问题清单（红卡不消化）；全红 = 需求不成熟，停下报告，不硬写。
7. **护栏**：不得引入用户未提及的概念/功能/角色——「顺便加个 X」是 AI 发明，须先问再写。

### 2. FISU 标注

【事实】=用户确认原话转述；【推断】=AI 补全待确认（须列依据）；【建议】=AI 专业建议可拒绝；未知→开放问题清单。**推断条目签字前必须逐条点名确认**——被消化进正文的推断是理解漂移的种子。

### 3. 写 Spec

模板 `.zcode/harness/templates/Product-Spec.md`，落项目根 `Product-Spec.md`。规模定档 S/M/L（决定后续架构/DFX 是否强制）。首次创建 `Product-Spec-CHANGELOG.md`；此后需求变更**成对更新** Spec + CHANGELOG（只改一个不算完成）。

### 4. 复述与签字

签字前用具体业务情境走一遍三段式：「我理解：〔角色〕在〔情境〕下做〔事〕是为了〔目的〕；我假设：…；请纠偏」。**未复述的签字只是版本批**——文档对了、理解错了照样做歪。内容变更须重新请批并重走复述（rules/workflow.md 签字闸）。

## 收敛条件（充足度判据）

业务上下文四要素齐（为什么做/谁受益/怎么运转/例外）+ 每 REQ 有 example + 推断已逐条点名 → 可请签字。缺任一 → 继续问，或显式记未知进红卡——不硬凑、不消化。红卡未清或未被用户显式接受 → 不进入签字（红卡是阻断项不是装饰）。

## 对话示例（好/坏对照）

坏：「请描述你的需求。」
好：「我看了 orders 模块——导出是 CSV 全量、财务月末手工对账。这是给财务对账用的，还是运营做日报？两者对及时性要求差很远。」

坏：「要做智能推荐吗？」
好：「推荐是像淘宝首页那种个性化，还是基于规则的固定排序？前者要埋点与数据积累，后者本周就能上。」

坏：（用户：「都行。」）「好的，那我看着办。」
好：（用户：「都行。」）「按 A 代价是 X，按 B 代价是 Y——选一个。」

## 交接

业务上下文章节 = 下游全链锚点源：架构需求映射表、DEV-PLAN、派单信封 `Business:` 字段（从它摘 2-3 句，子代理唯一的业务理解来源）全部回指这里。改本章节要同步检查下游锚点是否跟着变。

## 纪律

- 禁止替用户回答开放问题；列出来让用户拍板。
- 每条 REQ 必须可验证（能写出「跑什么命令/做什么操作算过」）且至少挂一个 example。
- 禁用模糊词做结论：「类似 X」「智能一点」「更好的」不是需求，逼成可判定陈述。
- 修订时先读现有 Spec 全文，增量修改，不重写风格。
- 【建议】被拒绝不是需求变更——记下拒绝理由即可，不纠缠。

## 回执

产出文件 + 业务上下文四要素状态（各：齐/缺）+ 推断项数（已点名/待点名）+ 开放问题数 + 待签字确认项清单。

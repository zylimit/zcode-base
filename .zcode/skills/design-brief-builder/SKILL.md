# design-brief-builder：视觉方向采访

## 目标

用户不是设计师——问「你要什么风格」等于没问。本 skill 用资深设计师采访甲方的方式，把模糊视觉感受逼成可执行的 Design-Brief.md（方向级，不问像素），衔接 product-spec-builder（上游）与 dev-planner/dev-builder（下游）。

## 依赖检测（启动第一步）

- Product-Spec.md 缺失 → 先路由 product-spec-builder（没有功能清单的视觉采访是无锚采访）。
- 设计工具 MCP 未连接 → 标注「手动设计模式」，Brief 照常生成，用户自行喂给设计工具。

## 第一性原则

- **选择题优先**：永远给 2-3 个具体选项，不给开放题。
- **参考锚定**：用真实产品当锚点，不用抽象形容词。「像 Linear 还是像 Notion？」比「你要简洁还是丰富？」有效十倍。
- **感受翻译**：用户说感受（「我要高级感」）→ 翻译成设计语言（「深色主题、低饱和度、大留白、衬线标题」）→ 复述给用户确认。
- **不问像素**：圆角/阴影/间距/字号/hex 色值是设计工具与实现的事，本 skill 只定方向。
- **联网优先**：设计趋势与竞品风格变化快，不凭过期记忆——涉及趋势/竞品/某功能主流设计方案时先 WebSearch 再推荐（搜索结果支撑建议，不复读）。

## 采访维度

**必须探明**（缺了设计只能猜）：

| 维度 | 逼法 |
|---|---|
| 情绪方向 | 「更接近 [参考A] 的 XX 路线还是 [参考B] 的 YY 路线？」追到 3 个关键词 + ≥1 个参考产品 |
| 色彩方向 | 冷/暖/中性 × 深/浅 + 品牌色有无；基于情绪方向给 2-3 个配色方案（各附参考）让选 |
| 信息密度 | 从 Spec 功能数推断：「一屏尽量多（像紧凑参考）还是每次聚焦一件事（像宽松参考）？」 |
| 核心功能视觉 | Spec 中每个有 UI 的功能逐个确认视觉方向（表格像 Airtable 还是 Excel？侧边栏折叠吗？）；Spec 每个有 UI 的功能必须有对应页面与关键状态变体（空/加载/错误态）——没定义的不算完成 |

**尽量探明**：反面参考（讨厌什么，例子具体）/ 品牌资产（logo、既有品牌色）/ 交互风格（动画多少、节奏快慢）/ 目标用户审美（开发者偏深色极简、消费者偏亲切活泼、企业偏稳重一致）。

**矛盾检测**：用户要「简洁」但产品一屏 20 个指标 → 直接指出冲突，给「Linear 折叠分页」vs「Grafana 全铺开排版干净」二选一，逼取舍。偏好打架时不许「都要」，逼排序。

## Design-Brief.md 输出结构

```
# Design-Brief
## 情绪方向（3 关键词 + 参考产品）
## 色彩方向（冷暖/深浅 + 品牌色，不定 hex）
## 信息密度（紧凑/适中/宽松 + 参考基准）
## 核心功能视觉（逐功能：方向 + 参考 + 关键状态变体）
## 反面参考（不要什么）｜交互风格｜[待补充] 标注未尽项
```

## 信息充足度判断

「必须探明」四项全达成才生成 Brief；未达成继续追问，不勉强生成。「尽量探明」未达成可生成但逐项标注 `[待补充]`。

## 纪律

- 用户说「都行/你看着办」→ 用选项逼出偏好，不接受含糊。
- 抽象词不做结论：「现代感」不是结论，「像 Linear 的冷色极简」才是。
- 翻译完必须复述确认（「我理解得对吗？」）——未确认的翻译只是自嗨。
- 生成后引导下一步：Brief 交 dev-planner（进开发计划）或直接交 dev-builder。

## 回执

Design-Brief.md 路径 + 四必须项达成清单 + 用户确认记录 + [待补充] 清单。
